# 第1章 作るRDBMSと作らないRDBMS

RDBMSは、パーサー、オプティマイザ、実行エンジン、ストレージエンジン、トランザクション管理、ネットワーク層という、性質の異なる複数のサブシステムから成り立っています。
それぞれのサブシステムには複数の実装方式があり、商用製品やOSS実装は互いに異なる方式を選んでいます。

この教材は、それらすべてを比較検討する概論ではありません。
各サブシステムについて実装方式を一つずつ選び、依存関係の順に積み上げて、単一ノードで動く小規模なRDBMSを最後まで完成させます。

本章では、完成物の姿、選んだ技術とその理由、対応するSQLの範囲、扱わない範囲、そして全40章のロードマップを定めます。

## 完成するもの

最終的に完成するのは、次の性質を持つRDBMSです。

- **単一ノード**で動作する(分散やレプリケーションは行わない)
- **行指向**でタプルを格納する
- **ディスクに永続化**し、プロセスを再起動してもデータが残る
- **トランザクション**に対応し、複数のトランザクションを並行実行できる

実装は、まずライブラリとして組み込む**Embedded API**から始めます。

```rust
let mut db = Database::open("example.db")?;
let result = db.execute("SELECT id, name FROM users WHERE id > 0")?;
```

この形態であれば、ネットワーク層やプロセス間通信を後回しにしたまま、SQL実行エンジンとストレージエンジンの検証に集中できます。
Client/Server化は最後の部(第6部)で行い、それまでに作ったEmbedded API層をそのままサーバープロセスの内部で呼び出す構造にします。

## 技術選定

RDBMSの各領域には複数の実装方式があります。
Strict Two-Phase LockingとMVCC、B+TreeとLSM-Tree、Volcano型実行とVectorized実行を同時に実装すると、章が進むごとに分岐が増え、どの章がどの方式に依存しているかを読者が追えなくなります。

この教材では、各領域で次の一方式に固定します。

| 領域 | 採用する方式 | 扱わない代替方式 |
| --- | --- | --- |
| テーブル格納 | Heap File + Slotted Page | LSM-Tree、列指向 |
| インデックス | B+Tree | Learned Index、Hash Index |
| 実行方式 | Volcano型のPull Executor | Vectorized Execution、JIT Compilation |
| 最適化 | ルールベース + 小規模なコストベース | Cascades、適応的最適化 |
| 並行性制御 | Strict Two-Phase Locking | MVCC |
| リカバリ | WAL + ARIES-lite | Shadow Paging、分散ログ |
| 通信 | 独自の単純なフレームプロトコル | PostgreSQL Wire Protocol |

代替方式を外す理由は、それぞれ異なります。

**LSM-Treeと列指向**は、書き込み最適化や分析クエリ向けの設計であり、行指向のOLTP的なワークロードを前提とする本編の題材とは、そもそも最適化の方向が逆になります。
Heap File + Slotted Pageのほうが、B+Treeやバッファプールと組み合わせたときの学習の連続性が高くなります。

**Learned Index**は、データ分布に対する回帰モデルを事前学習する必要があり、B+Treeの構造そのものを学ぶという本編の目的からは外れます。

**Vectorized ExecutionとJIT Compilation**は、Volcano Executorが確立した後の高速化技法であり、先に確立すべきタプル単位の実行モデルなしには意味を持ちません。

**MVCC**は、タプルにバージョン情報を持たせ、可視性判定・GC・インデックスとの整合という広い範囲に影響します。
Strict 2PLと同じ章群の中で両方を実装すると、どちらの制約でロックやタプル形式を設計しているのかが不明瞭になります。
本編ではStrict 2PLで並行性制御を完成させ、MVCCは発展編で別実装として扱います。

**Shadow Paging**は、更新のたびにページ全体を複製する方式であり、WALより単純だが書き込み増幅が大きくなります。
Crash RecoveryにARIESの考え方を使うほうが、商用RDBMSの実装に近い知識になります。

**PostgreSQL Wire Protocol**は、認証方式やメッセージ種別が多く、通信プロトコルの学習よりプロトコル仕様の実装に時間を取られます。
本編では独自の単純な長さ付きフレームで通信の基本(フレーミング、リクエスト/レスポンスの対応、エラー伝達)を学び、既存プロトコルへの互換は発展編に回します。

外した代替方式は、消えるわけではありません。
MVCC、高度なSQL、Vectorized Execution、LSM-Tree、PostgreSQL互換プロトコルは、いずれも本編完成後の発展編で扱う候補です。

## 対応するSQLサブセット

完成時に実行できるSQLは、次の範囲に限定します。

```sql
CREATE TABLE
DROP TABLE
CREATE INDEX
DROP INDEX

INSERT
UPDATE
DELETE

SELECT ... FROM ...
WHERE
INNER JOIN
GROUP BY
HAVING
ORDER BY
LIMIT
DISTINCT

BEGIN
COMMIT
ROLLBACK

EXPLAIN
EXPLAIN ANALYZE
```

データ型は、`BIGINT`、`BOOLEAN`、`TEXT`、`NULL`から始めます。
`DOUBLE`は、式評価と型変換の基礎を固めた後に追加します。

制約は`NOT NULL`、`PRIMARY KEY`、`UNIQUE`までを本編の対象とします。
外部キー、トリガー、ビュー、ウィンドウ関数、サブクエリ、再帰CTEは、いずれも発展編Bで扱います。

## 非目標

次の項目は、本編では実装しません。

- **分散処理**(パーティショニング、レプリケーション、分散トランザクション)
- **SQL標準への完全互換**(標準の広い範囲ではなく、上記サブセットに限定する)
- **認証・認可**(ユーザー管理、権限制御)
- **TLSなどの通信の暗号化**
- **非同期I/O**(Tokioなどによる非同期化はEmbedded API完成後の別編とする)

これらを外す理由は、単純化のためではありません。
分散処理や認証は、単一ノードのストレージエンジンやトランザクション処理が正しく動いて初めて意味を持つ層であり、土台が固まる前に手を広げると、どの章もどちらの問題を解いているのか判別できなくなります。

## ロードマップ

全40章は第0部から第6部までの7部構成であり、各部の終わりに到達点を置きます。

| 部 | 到達点 | 対応する章 |
| --- | --- | --- |
| 第0部 設計と開発環境 | 開発の土台(エラー型、テスト基盤)が揃う | 第1〜3章 |
| 第1部 Bare Bones | インメモリSQLデータベースが動く | 第4〜10章(到達点は第10章) |
| 第2部 Storage | 再起動可能なディスクRDBMSがSQLレベルで動作する | 第11〜16章(到達点は第16章) |
| 第3部 Query Execution | Join、Aggregate、Index Scanに対応する | 第17〜25章(到達点は第25章) |
| 第4部 Query Optimizer | コストベース最適化に対応する | 第26〜29章(到達点は第29章) |
| 第5部 Transaction | 並行実行・WAL・Crash Recoveryに対応する | 第30〜35章(到達点は第35章) |
| 第6部 Server、運用、品質保証 | Client/Server型の小規模RDBMSが完成する | 第36〜40章(到達点は第40章) |

途中の主な到達点は次の通りです。

- 第10章終了時点で、ディスクを使わないインメモリSQLデータベースが動く
- 第16章終了時点で、プロセスを再起動してもテーブルとデータが残る
- 第25章終了時点で、複数テーブルのJoin、集約、インデックス検索がSQLから実行できる
- 第29章終了時点で、統計情報とコストモデルに基づいてアクセスパスとJoin順序を選べる
- 第35章終了時点で、複数トランザクションを並行実行しつつ、クラッシュ後もコミット済みデータを復元できる
- 第40章終了時点で、TCP経由でクライアントから接続できるClient/Server型のRDBMSになる

## 教材の進め方

各章は次の形式で統一します。

1. 前章の実装でできないことを、テストやベンチマークで再現する
2. 必要なデータベース理論を説明する
3. 守るべき不変条件を明示する
4. Rustで最小限の実装を追加する
5. 単体テストと統合テストを書く
6. 故障、競合、境界値を再現する
7. 演習問題を示す

この形式は、`Writing an OS in Rust`が確立した進め方を踏襲しています。
同教材の特徴は、各記事が小さな完結したチュートリアルであり、必要なコードが記事内に閉じていて、対応するリポジトリの状態を常に確認できる点にあります。

本教材でも、各章に`chapter-XX-start`と`chapter-XX-final`のGitタグを付け、章の始点と終点のコード状態を追跡できるようにします。
ある章を終えると、必ずその状態でコンパイルが通り、テストが通り、前章より一つ明確な機能が増えています。
次の第2章では、この一つ一つの章が積み上がっていく先の全体像として、SQLがLexerからStorage Engineまでどのような経路を通るかを概観します。
